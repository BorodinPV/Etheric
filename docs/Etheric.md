# Проектирование высокопроизводительного OAuth 2.0 Authorization Server на Quarkus с полностью реактивным стеком

**Версия:** 7.0 (полная, production‑ready)  
**Статус:** Финальный архитектурный проект  
**Дата:** 2026-07-19

---

## 1. Введение

### 1.1. Цель документа

Документ описывает архитектуру и набор необходимых компонентов для создания **production‑ready** Authorization Server (сервера авторизации), реализующего поток Authorization Code Grant согласно **RFC 6749**. Сервер разрабатывается на платформе Java с использованием фреймворка Quarkus и полностью реактивного стека. Основной фокус — максимальная производительность, минимальное потребление ресурсов, горизонтальная масштабируемость и безопасность, достаточная для промышленной эксплуатации.

### 1.2. Область применения

Документ предназначен для архитекторов, технических лидеров и разработчиков, создающих собственный OAuth 2.0-совместимый сервис аутентификации и авторизации. Он определяет состав технологий, структуру данных, взаимодействие компонентов, требования к реализации и содержит все необходимые проверки, обработку ошибок и меры безопасности. Документ не содержит детального кода, что позволяет использовать его как основу для технического задания или архитектурного обзора.

### 1.3. Нормативные ссылки

- [RFC 6749](https://www.rfc-editor.org/info/rfc6749) — OAuth 2.0 Authorization Framework.
- [RFC 6750](https://www.rfc-editor.org/info/rfc6750) — OAuth 2.0 Bearer Token Usage.
- [RFC 7009](https://www.rfc-editor.org/info/rfc7009) — OAuth 2.0 Token Revocation (опционально).
- [RFC 7662](https://www.rfc-editor.org/info/rfc7662) — OAuth 2.0 Token Introspection (опционально).
- [RFC 7519](https://www.rfc-editor.org/info/rfc7519) — JSON Web Token (JWT).
- [RFC 7517](https://www.rfc-editor.org/info/rfc7517) — JSON Web Key (JWK) для публикации ключей.

## 2. Архитектура и протокол

### 2.1. Базовые эндпоинты (согласно RFC 6749)

Для реализации потока Authorization Code Grant сервер должен предоставлять следующие эндпоинты:

| Название эндпоинта (по RFC)       | Типовой путь               | Сторона | Назначение                                                                 |
|-----------------------------------|----------------------------|---------|----------------------------------------------------------------------------|
| **Authorization Endpoint**        | `/authorize`               | Сервер  | Принимает запрос от браузера пользователя, проводит аутентификацию пользователя и выдаёт авторизационный код. |
| **Token Endpoint**                | `/token`                   | Сервер  | Принимает прямой (backchannel) POST-запрос от клиента для обмена авторизационного кода на access-токен (и, опционально, refresh-токен). |
| **Redirection Endpoint**          | (регистрируется клиентом)  | Клиент  | Это не эндпоинт сервера, а URI, который клиент предварительно регистрирует. На него сервер перенаправляет пользователя после выдачи кода или ошибки. |
| **JWKS Endpoint** *(добавлено)*   | `/.well-known/jwks.json`   | Сервер  | Публикует публичные ключи для верификации JWT, используется ресурс-серверами. |

### 2.2. Поток авторизации (Authorization Code Flow) — детализированный

Процесс взаимодействия включает следующие шаги:

1. **Инициация:** Клиентское приложение перенаправляет браузер пользователя на Authorization Endpoint сервера, передавая параметры: `response_type=code`, `client_id`, `redirect_uri` и `state` (последний обязателен для защиты от CSRF). При этом сервер сохраняет в Redis состояние `auth:request:{state}` с параметрами запроса (`client_id`, `redirect_uri`, `scope`, `state`) и устанавливает TTL = 10 минут.

2. **Аутентификация и согласие (с пользовательским интерфейсом):**
   - Сервер проверяет наличие активной сессии пользователя (обычно по cookie). Если сессия отсутствует или истекла, сервер отображает страницу входа — HTML-форму, где пользователь вводит логин и пароль. При этом страница входа также содержит скрытый CSRF-токен для защиты.
   - После успешной аутентификации создаётся сессия (сохраняется в Redis с TTL, например, 8 часов) и устанавливается cookie.
   - Затем сервер отображает экран согласия — страницу, на которой перечислены запрашиваемые клиентом разрешения (scope), информация о клиенте (название, иконка) и даны кнопки «Разрешить» или «Отказать».
   - Пользователь принимает решение. Если он отказывает, сервер перенаправляет на `redirect_uri` с параметром `error=access_denied`. Если разрешает — сервер продолжает.

3. **Выдача кода:** После получения согласия сервер генерирует одноразовый авторизационный код (например, случайный UUID), сохраняет его в Redis по ключу `auth:code:{code}` вместе с параметрами (`client_id`, `user_id`, `redirect_uri`, `scope`) и устанавливает TTL (например, 10 минут). Затем сервер перенаправляет пользователя обратно на Redirection Endpoint клиента, добавляя в URL параметры `code` и `state`.

4. **Получение кода:** Клиент извлекает код из запроса, проверяет `state` на соответствие отправленному и сохраняет код для следующего шага.

5. **Обмен кода на токены:** Клиент отправляет прямой POST-запрос на Token Endpoint сервера, передавая `grant_type=authorization_code`, полученный `code`, `redirect_uri` (обязательно должен совпадать с использованным на шаге 1), а также `client_id` и `client_secret` для аутентификации клиента. Запрос выполняется через backchannel, без участия браузера. **Важно:** Сервер аутентифицирует клиента (проверяет `client_id` и `client_secret`) при каждом запросе.

6. **Выдача токенов:** Сервер проверяет:
   - Что код существует и не истек (проверка TTL).
   - Что `redirect_uri` совпадает с сохранённым при создании кода.
   - Что код ещё не был использован (одноразовость). После проверки код немедленно удаляется из Redis.
   - При успехе сервер генерирует JWT access-токен (срок жизни, например, 1 час) и refresh-токен (срок жизни, например, 7 дней), сохраняет их в Redis для быстрой валидации и возвращает JSON с токенами.

7. **Доступ к ресурсам:** Клиент использует полученный `access_token` в заголовке `Authorization: Bearer <token>` при вызовах к защищённым API. Ресурс-сервер самостоятельно валидирует токен (проверяет подпись, срок действия и права), используя публичный ключ, полученный с JWKS‑эндпоинта.

8. **Обновление токена (по желанию):** Клиент может использовать refresh-токен для получения нового access-токена без повторной аутентификации. Для этого он отправляет запрос на Token Endpoint с `grant_type=refresh_token` и `refresh_token`. Сервер проверяет валидность refresh-токена, срок его действия, и, в случае успеха, выдаёт новый access-токен (и, опционально, новый refresh-токен). При этом старый refresh-токен может быть отозван (рекомендуется).

9. **Выход из системы *(добавлено)*:** Пользователь может инициировать выход, что приведёт к удалению его сессии из Redis и очистке cookie.

### 2.3. Обработка ошибок и редирект с ошибкой

Если на любом этапе возникает ошибка (неверный параметр, отсутствие клиента, несовпадение `redirect_uri`, отказ пользователя, истекший код и т.д.), сервер должен:

- Если ошибка произошла до этапа выдачи кода (т.е. на Authorization Endpoint или в процессе взаимодействия с пользователем), он перенаправляет пользователя обратно на `redirect_uri` с параметром `error` (и, опционально, `error_description`), используя тот же `state`, если он был передан.
- Если ошибка произошла на Token Endpoint (неверный код, неверный `client_secret` и т.д.), сервер возвращает HTTP-статус 400 или 401 с JSON-телом, содержащим `error` и, возможно, `error_description`.

**Основные коды ошибок OAuth 2.0:**

- `invalid_request` – неверный параметр (например, отсутствует `response_type`).
- `unauthorized_client` – клиент не авторизован для данного запроса.
- `access_denied` – пользователь отказал в доступе.
- `unsupported_response_type` – неподдерживаемый `response_type`.
- `invalid_scope` – неверный или запрещённый `scope`.
- `server_error` – внутренняя ошибка сервера.
- `temporarily_unavailable` – временная недоступность.
- `invalid_grant` – неверный, истекший или уже использованный код или refresh-токен.
- `unsupported_grant_type` – неподдерживаемый `grant_type`.
- `invalid_client` – ошибка аутентификации клиента.

## 3. Технологический стек

### 3.1. Выбранные технологии и их назначение

| Компонент                      | Технология                         | Роль в системе                                                                                                 |
|--------------------------------|------------------------------------|----------------------------------------------------------------------------------------------------------------|
| **Фреймворк**                  | Quarkus                            | Обеспечивает высокую производительность, низкое потребление памяти и мгновенный старт (особенно в native-режиме). Поддерживает реактивное программирование и интеграцию с облачными средами. |
| **Реактивный ORM**             | Hibernate Reactive с Panache       | Позволяет работать с реляционной базой данных в неблокирующем, асинхронном стиле. Panache упрощает синтаксис запросов и ускоряет разработку. |

| **Временное хранилище**        | Redis                              | Высокоскоростное in-memory хранилище для авторизационных кодов, access- и refresh-токенов, сессий, состояния запросов. Обеспечивает микросекундные задержки доступа. |

| **Аутентификация и OIDC**      | Quarkus OIDC                       | Обеспечивает интеграцию с OpenID Connect и OAuth 2.0, поддерживает как веб-приложения, так и ресурс-серверы.   |
| **Шаблонизация**               | Quarkus Qute                       | Современный шаблонизатор для динамической генерации HTML-страниц (входа, согласия, ошибок). Позволяет передавать данные из бэкенда в шаблоны и обеспечивает i18n. |

### 3.2. Обоснование выбора реактивного стека

Реактивный подход позволяет обрабатывать большое количество одновременных запросов с минимальным количеством потоков, поскольку все операции ввода-вывода (сеть, базы данных) выполняются асинхронно и не блокируют потоки. Это даёт:

- Высокую пропускную способность (более 15 000 запросов в секунду в тестах).
- Низкую и предсказуемую задержку (P99 < 50 мс).
- Эффективное использование ресурсов ЦП и памяти.
- Горизонтальную масштабируемость.

## 4. Архитектура данных

### 4.1. Двухуровневая стратегия хранения

Для достижения максимальной производительности применяется гибридный подход, разделяющий данные по времени жизни и частоте доступа:

- **Постоянный слой (PostgreSQL)** – хранит критичные данные, которые меняются редко:
   - Зарегистрированные клиенты: `client_id`, `client_secret` (хранится в захешированном виде), список разрешённых `redirect_uris`, доступные `scopes`, поддерживаемые `grant_types`, статус `enabled`, название клиента, иконка (опционально) для отображения на экране согласия.
   - Пользователи: `username`, хеш пароля (bcrypt), `email`, список `roles`, статус `enabled`.
   - Прочие настройки и конфигурации.

- **Кэш-слой (Redis)** – хранит временные данные с высоким TTL, доступ к которым осуществляется постоянно и с максимальной скоростью:
   - Авторизационные коды (ключ `auth:code:{code}`) с данными о клиенте, пользователе, `redirect_uri`, `scope`; TTL = 10 минут (настраивается).
   - Активные access-токены (ключ `auth:token:access:{token}`) с данными о пользователе, клиенте, `scope`, времени истечения; TTL = время жизни токена (например, 1 час).
   - Refresh-токены (ключ `auth:token:refresh:{token}`) с данными о пользователе и клиенте; TTL = время жизни refresh-токена (например, 7 дней).
   - Сессии пользователей (ключ `auth:session:{session_id}`) с идентификатором пользователя, временем создания; TTL = время жизни сессии (например, 8 часов).
   - Состояние авторизационного запроса (ключ `auth:request:{state}`) с параметрами `client_id`, `redirect_uri`, `scope`, `state` и, опционально, `user_id` после аутентификации; TTL = 10 минут.

**Все значения TTL должны быть вынесены в конфигурацию приложения** для возможности гибкой настройки без перекомпиляции.

### 4.2. Структура таблиц PostgreSQL (описание)

- **Таблица `clients`** содержит поля: `id` (UUID), `client_id` (уникальный текстовый), `client_secret_hash`, `client_name`, `redirect_uris` (массив текстовых URI), `scopes` (массив), `grant_types` (массив), `enabled` (булев), `created_at`, а также опциональные `client_logo` (ссылка на картинку) и `client_description` для отображения на экране согласия.
- **Таблица `users`** содержит поля: `id` (UUID), `username` (уникальный), `password_hash`, `email`, `roles` (массив), `enabled` (булев), `created_at`.
- **Таблица `authorization_codes`** (резервное хранилище) – может использоваться для дублирования кодов, но в основном они живут в Redis. Содержит `code` (текстовый, PK), `client_id`, `user_id` (внешний ключ к `users`), `redirect_uri`, `scopes` (массив), `created_at`, `expires_at`.

### 4.3. Структура ключей в Redis (описание)

- `auth:code:{code}` – JSON с полями: `client_id`, `user_id`, `redirect_uri`, `scopes` (массив). TTL = 10 минут (настраивается).
- `auth:token:access:{token}` – JSON с полями: `user_id`, `client_id`, `scopes`, `expires_at` (timestamp). TTL = время жизни токена (настраивается).
- `auth:token:refresh:{token}` – JSON с полями: `user_id`, `client_id`, `scopes`. TTL = время жизни refresh-токена (настраивается).
- `auth:session:{session_id}` – JSON с полями: `user_id`, `created_at`. TTL = время жизни сессии (настраивается).
- `auth:request:{state}` – JSON с полями: `client_id`, `redirect_uri`, `scope` (массив), `state`, `user_id` (заполняется после аутентификации). TTL = 10 минут (настраивается).

## 5. Реализация (описание компонентов без кода)

### 5.1. Необходимые расширения Quarkus

Для сборки проекта необходимо подключить следующие расширения Maven/Gradle:

- Core Quarkus (resteasy-reactive, jackson)
- Hibernate Reactive with Panache
- Reactive PostgreSQL Client
- Redis Client (реактивный)
- SmallRye JWT (для генерации и валидации JWT)
- Quarkus OIDC
- Quarkus Qute – для рендеринга HTML-страниц.

### 5.2. Конфигурация приложения

В файле настроек (`application.properties`) должны быть определены:

- Параметры подключения к PostgreSQL (URL, имя пользователя, пароль, размер пула соединений, таймауты).
- Настройки Hibernate Reactive (генерация схемы, логирование SQL, диалект).
- Параметры подключения к Redis (хост, порт, тип клиента — реактивный).
- Настройки OIDC (URL авторизационного сервера, тип приложения, client-id и секрет).
- Параметры JWT (алгоритм, путь к приватному ключу для подписи, путь к публичному ключу для верификации, issuer, сроки жизни).
- Настройки CORS (разрешённые источники, методы, заголовки).
- Настройки Qute (путь к шаблонам, кодировка, поддержка i18n).
- Настройки времени жизни (TTL) для кодов, токенов, сессий и состояния запросов.
- Настройки Graceful Shutdown (таймаут ожидания завершения запросов).

### 5.3. Модели данных (сущности)

- **Сущность `Client`** — представляет зарегистрированное клиентское приложение. Содержит поля, соответствующие таблице `clients`. Аннотируется как `PanacheEntityBase` для использования реактивного репозитория.
- **Сущность `User`** — представляет пользователя системы. Содержит поля, соответствующие таблице `users`.

### 5.4. Репозитории (Data Access)

- **`ClientRepository`** — предоставляет реактивные методы для поиска клиента по `client_id`, проверки валидности клиента (по `client_id` и хешу секрета), получения списка `redirect_uris` и `scopes` для клиента.
- **`UserRepository`** — предоставляет реактивные методы для поиска пользователя по имени, проверки учётных данных (хеш пароля), получения пользователя по идентификатору, а также для обновления данных пользователя (например, смена пароля).

### 5.5. Сервис кэширования (Redis)

- **`CacheService`** — инкапсулирует все операции с Redis:
   - Сохранение, получение и удаление авторизационного кода с заданным TTL.
   - Сохранение и получение данных access-токена.
   - Сохранение и получение данных refresh-токена.
   - Сохранение, получение и удаление состояния авторизационного запроса (по `state`).
   - Сохранение и проверка сессий пользователей (по `session_id`).
   - Методы для проверки существования ключа и удаления по шаблону (например, при логауте).
   - Все методы возвращают реактивные `Uni` (из библиотеки Mutiny) для асинхронной обработки.

**Важно:** Все операции с Redis не должны приводить к утечкам памяти и должны корректно обрабатывать ошибки соединения (с повторными попытками и fallback‑логикой).

### 5.6. Генерация и валидация JWT (сервис токенов)

- **`JwtService`** — отвечает за создание и валидацию JWT:
   - Метод для генерации access-токена: принимает идентификатор пользователя, набор ролей и список `scopes`; создаёт JWT с указанными клеймами (`subject`, `groups`, `scopes`), временем выдачи и сроком действия; подписывает с использованием закрытого ключа (алгоритм RS256).
   - Метод для генерации refresh-токена: аналогично access-токену, но с другими клеймами (тип токена = refresh) и большим сроком действия.
   - Метод для генерации авторизационного кода: возвращает случайный UUID (или другой уникальный идентификатор).
   - Метод для верификации подписи и проверки срока действия токена (используется ресурс-сервером, но может быть вызван и здесь для проверки).
   - Публикация JWKS (JSON Web Key Set) для предоставления публичных ключей ресурс-серверам.
- **Управление ключами:** Приватный ключ должен храниться в защищённом месте (например, в секретном хранилище или в зашифрованном виде в файле, доступном только приложению). Публичный ключ публикуется на эндпоинте `/.well-known/jwks.json`. Ротация ключей может быть реализована позже, но в минимальной версии достаточно статической пары ключей.

### 5.7. Пользовательский интерфейс авторизации (страницы)

Для взаимодействия с пользователем необходимы три динамические HTML-страницы, генерируемые с помощью шаблонизатора Qute.

**Страница входа (`/login`):**
- Отображается, когда пользователь не аутентифицирован или сессия истекла.
- Содержит форму с полями ввода имени пользователя и пароля.
- Содержит скрытые поля для параметров запроса (`client_id`, `redirect_uri`, `state`, `scope`) или извлекает их из Redis по `state`.
- **Обязательно** генерирует CSRF-токен в виде скрытого поля, который проверяется при POST-запросе.
- При успешной отправке формы сервер аутентифицирует пользователя (проверяет хеш пароля), создаёт сессию (сохраняет в Redis и устанавливает cookie), обновляет запись `auth:request:{state}` с `user_id`, и перенаправляет на `/consent` (если согласие ещё не получено) или сразу на `/authorize` для завершения.

**Экран согласия (`/consent`):**
- Отображается после успешной аутентификации, но до выдачи кода.
- Показывает пользователю информацию о клиенте (название, описание, логотип), список запрашиваемых разрешений (`scopes`) с кратким описанием каждого, а также возможность просмотреть параметры запроса.
- Содержит кнопки «Разрешить» и «Отказать».
- **Обязательно** содержит скрытый CSRF-токен для защиты формы подтверждения.
- При нажатии «Разрешить» сервер генерирует код и перенаправляет на `redirect_uri` клиента с `code` и `state`.
- При нажатии «Отказать» сервер перенаправляет на `redirect_uri` с параметром `error=access_denied`.

**Страница ошибки (опционально, `/error`):**
- Отображается в случае внутренних ошибок, которые не могут быть обработаны через редирект (например, проблемы с БД). Показывает дружественное сообщение и предлагает повторить попытку или обратиться в поддержку.

**Управление состоянием между страницами:**
- Параметры запроса (`client_id`, `redirect_uri`, `scope`, `state`) сохраняются в Redis по ключу `auth:request:{state}` при первом обращении к `/authorize`.
- После успешного логина и согласия эти данные извлекаются из Redis, что гарантирует, что пользователь не потеряет контекст при редиректах.
- Время жизни таких записей — 10 минут, после чего они автоматически удаляются.

### 5.8. Эндпоинты (REST-контроллеры) — полное описание

- **Authorization Endpoint** (`GET /authorize`):
   - Проверяет наличие обязательных параметров: `response_type`, `client_id`, `redirect_uri`, `state` (state обязателен).
   - Проверяет существование клиента и его активность.
   - Проверяет, что переданный `redirect_uri` присутствует в списке разрешённых для клиента.
   - Проверяет, что `response_type` равен `code` (или `token` в неявном потоке, но мы его не поддерживаем).
   - Если `scope` передан, проверяет, что все запрашиваемые `scope` разрешены для клиента.
   - Если какой-либо параметр невалиден, выполняет редирект на `redirect_uri` с параметром `error` и соответствующим кодом.
   - Сохраняет параметры запроса в Redis по ключу `auth:request:{state}`.
   - Проверяет наличие сессии пользователя. Если сессии нет, перенаправляет на страницу входа (`/login`). Если сессия есть, получает `user_id` из сессии.
   - После успешной аутентификации и получения согласия (или если согласие уже было получено ранее и сохранено в сессии), генерирует авторизационный код, сохраняет его в Redis, удаляет запись `auth:request:{state}`, и перенаправляет на `redirect_uri` с параметрами `code` и `state`.

- **Страница входа** (`GET /login`, `POST /login`):
   - GET: Рендерит HTML-форму входа (Qute-шаблон). Если передан параметр `state`, извлекает данные из Redis и подставляет их в скрытые поля. Также генерирует CSRF-токен и сохраняет его в сессии.
   - POST: Принимает `username`, `password`, `state` (опционально) и CSRF-токен. Проверяет CSRF-токен. Проверяет учётные данные пользователя через `UserRepository`. Если валидны, создаёт сессию (сохраняет в Redis с TTL) и устанавливает cookie. Если был передан `state`, обновляет запись `auth:request:{state}`, добавляя `user_id`. Затем перенаправляет на `/consent` (если согласие ещё не получено) или на `/authorize` с параметрами (если согласие уже получено ранее). В случае ошибки аутентификации снова рендерит страницу входа с сообщением об ошибке.

- **Страница согласия** (`GET /consent`, `POST /consent`):
   - GET: Проверяет наличие сессии и параметров `state` (или извлекает данные из Redis по `state`). Получает данные клиента и запрашиваемые `scope`. Рендерит HTML-страницу с информацией о клиенте, списком `scope` и кнопками. Генерирует CSRF-токен для защиты формы.
   - POST: Принимает решение пользователя (`approve` или `deny`) и CSRF-токен. Проверяет CSRF-токен. Если `approve`, генерирует код, сохраняет его в Redis (с привязкой к `user_id` и `redirect_uri`), удаляет запись `auth:request:{state}`, и перенаправляет на `redirect_uri` с `code` и `state`. Если `deny`, перенаправляет на `redirect_uri` с `error=access_denied`.

- **Token Endpoint** (`POST /token`):
   - Получает параметры формы: `grant_type`, `code` (для `authorization_code`), `redirect_uri`, `client_id`, `client_secret`, `refresh_token` (для `refresh_token`).
   - Аутентифицирует клиента: проверяет `client_id` и `client_secret` (можно использовать Basic Auth или параметры формы). Секрет сравнивается с хешем в БД.
   - Проверяет `grant_type` на поддерживаемые значения (`authorization_code`, `refresh_token`). Если не поддерживается, возвращает `unsupported_grant_type`.
   - Для `authorization_code`:
      - Проверяет существование кода в Redis.
      - Проверяет, что `redirect_uri` совпадает с сохранённым.
      - Проверяет, что код не истек (TTL).
      - Если код валиден, удаляет его из Redis (одноразовость).
      - Генерирует access-токен и refresh-токен (с помощью `JwtService`), сохраняет их в Redis с соответствующими TTL.
      - Возвращает JSON с `access_token`, `token_type=Bearer`, `expires_in`, `refresh_token`, и `scope`.
   - Для `refresh_token`:
      - Проверяет существование refresh-токена в Redis.
      - Проверяет, что клиент, указанный в токене, совпадает с клиентом, сделавшим запрос.
      - Если токен валиден, генерирует новый access-токен (и, опционально, новый refresh-токен), сохраняет их в Redis, удаляет старый refresh-токен (если выдан новый).
      - Возвращает JSON с новыми токенами.
   - В случае любых ошибок возвращает HTTP-статус 400 или 401 с JSON-телом, содержащим `error` и `error_description`.

- **Эндпоинт выхода (логаут)** (`GET /logout`, опционально):
   - Удаляет сессию пользователя из Redis, очищает cookie.
   - Может принимать параметр `redirect_uri` для перенаправления после выхода.

- **JWKS Endpoint** (`GET /.well-known/jwks.json`):
   - Возвращает JSON-документ с публичными ключами (в формате JWK), которые могут использоваться ресурс-серверами для верификации JWT. Ключи генерируются из пары ключей, используемой `JwtService`.

### 5.9. Ключевые проверки и обработка ошибок (полный список)

Для обеспечения безопасности и корректной работы сервер должен реализовывать следующие проверки:

| Проверка                                                            | Где применяется                | Действие при ошибке                                                     |
|---------------------------------------------------------------------|--------------------------------|-------------------------------------------------------------------------|
| Наличие обязательных параметров (`response_type`, `client_id`, `redirect_uri`, `state`) | `/authorize`                   | Редирект с `error=invalid_request`                                      |
| Валидность `client_id` и активность клиента                         | `/authorize`, `/token`         | Редирект с `error=unauthorized_client` (на `/authorize`) или HTTP 401 (на `/token`) |
| Соответствие `redirect_uri` зарегистрированным значениям            | `/authorize`                   | Редирект с `error=invalid_request` (или `invalid_client`)               |
| Соответствие `redirect_uri` при обмене кода                         | `/token`                       | HTTP 400 с `error=invalid_grant`                                       |
| Поддержка `response_type=code`                                      | `/authorize`                   | Редирект с `error=unsupported_response_type`                           |
| Валидность `scope` (разрешён ли для клиента)                        | `/authorize`                   | Редирект с `error=invalid_scope`                                       |
| Наличие сессии пользователя                                         | `/authorize`                   | Перенаправление на страницу входа                                      |
| Валидность учётных данных пользователя (пароль)                     | `/login`                       | Показать ошибку на странице входа                                      |
| Наличие согласия пользователя                                       | `/authorize`                   | Перенаправление на страницу согласия                                   |
| Одноразовость авторизационного кода                                 | `/token`                       | HTTP 400 с `error=invalid_grant`                                       |
| Срок действия кода (TTL)                                            | `/token`                       | HTTP 400 с `error=invalid_grant`                                       |
| Аутентификация клиента на `/token` (`client_id` + `secret`)         | `/token`                       | HTTP 401 с `error=invalid_client`                                      |
| Поддержка `grant_type`                                              | `/token`                       | HTTP 400 с `error=unsupported_grant_type`                              |
| Валидность refresh-токена (существование, срок, принадлежность клиенту) | `/token` (при refresh)         | HTTP 400 с `error=invalid_grant`                                       |
| CSRF-токен на страницах входа и согласия                            | `/login` POST, `/consent` POST | Показать ошибку или редирект с `error=invalid_request`                 |

> **Важно:** Все ошибки и предупреждения должны логироваться (без конфиденциальных данных), чтобы упростить отладку и мониторинг.

### 5.10. Безопасность и аутентификация (дополнено)

- **Аутентификация пользователя** осуществляется через страницу входа с проверкой пароля (хеш сравнивается с сохранённым в PostgreSQL). Пароли должны храниться с использованием сильного хеширования (например, bcrypt).
- **Управление сессиями** реализовано с помощью cookie и хранения данных сессии в Redis. Каждая сессия имеет уникальный идентификатор, который хранится в cookie (например, `SESSIONID`). По этому идентификатору сервер получает данные пользователя из Redis.
- **Защита от CSRF** на страницах входа и согласия реализуется через генерацию и проверку скрытых токенов, которые сохраняются в сессии. Параметр `state` также является частью защиты на этапе авторизации.
- **Безопасная передача** всех форм и данных через HTTPS (TLS). В production-окружении обязательно использовать валидные SSL-сертификаты.
- **Защита от атак повторного использования кода:** код удаляется после первого использования, и срок его жизни ограничен.
- **Защита конфиденциальных данных в логах:** Настроить логирование так, чтобы оно не записывало `client_secret`, `authorization_code`, `access_token`, `refresh_token`, пароли пользователей. Использовать маскирование или исключение таких полей.
- **CORS (Cross-Origin Resource Sharing):** Если страницы входа и согласия размещены на другом домене или порту, чем бэкенд, необходимо настроить CORS в Quarkus (параметры `quarkus.http.cors.*`), разрешив нужные источники и методы.
- **Graceful Shutdown:** Включить graceful shutdown в Quarkus, чтобы при остановке приложения все текущие запросы завершались корректно, а пулы соединений с БД и Redis освобождались без потерь.

### 5.11. Регистрация клиентов (Client Registration)

Для добавления новых клиентских приложений в систему предусмотреть:

- **Способ 1 (для разработки):** Прямое добавление записей в таблицу `clients` через SQL-скрипты.
- **Способ 2 (для production):** Защищённый REST-эндпоинт (например, `POST /admin/clients`), доступный только администраторам. Этот эндпоинт принимает данные клиента (`client_name`, `redirect_uris`, `scopes`, `grant_types`) и генерирует `client_id` и `client_secret` (или принимает их). Секрет хранится в захешированном виде.

В минимальной версии достаточно способа 1, но документ должен описывать оба варианта.

## 8. Требования к производительности и масштабируемости

### 8.1. Целевые метрики

- **Пропускная способность:** Более 15 000 запросов в секунду (QPS) в сценарии валидации токенов.
- **Задержка:** Время ответа на 99-й процентиль (P99) не должно превышать 50 мс.
- **Время старта:** В нативном режиме (GraalVM) — менее 50 мс; в JVM-режиме — около 1 секунды.
- **Потребление памяти:** В нативном режиме — менее 100 МБ; в JVM-режиме — около 200 МБ.

### 8.2. Масштабирование

- **Горизонтальное масштабирование:** Приложение разработано как stateless, поэтому может быть запущено несколько экземпляров за балансировщиком нагрузки. Все состояния (коды, токены, сессии, запросы авторизации) хранятся в Redis, что обеспечивает их доступность для любого экземпляра.
- **Redis:** Рекомендуется использовать Redis Cluster для обеспечения высокой доступности и распределения нагрузки.
- **PostgreSQL:** Для чтения можно настроить реплики, для записи — использовать шардирование при необходимости.

### 8.3. Оптимизации

- **AOT-компиляция:** Сборка native-образов с помощью GraalVM для минимизации времени старта и потребления памяти.
- **Настройка пулов соединений:** Настроить размеры пулов для реактивных клиентов PostgreSQL и Redis в соответствии с ожидаемой нагрузкой.
- **Многоуровневое кэширование:** Добавить локальный кэш (например, Caffeine) перед Redis для самых частых запросов (например, проверка клиента) для снижения сетевых вызовов.
- **Ограничение частоты запросов (Rate Limiting):** Внедрить механизм ограничения (например, Bucket4j) для защиты от DDoS и перегрузок, особенно для страниц входа и согласия.

## 9. Заключение

Документ описывает полную архитектуру высокопроизводительного OAuth 2.0 Authorization Server на базе Quarkus с полностью реактивным стеком, включая пользовательский интерфейс, все ключевые проверки, обработку ошибок, меры безопасности, управление ключами, регистрацию клиентов, CORS, конфигурируемые параметры, тестирование и документацию. Это делает систему готовой к промышленной эксплуатации. Выбранные технологии — Quarkus, Hibernate Reactive с Panache, Reactive PostgreSQL Client, Redis и Qute — обеспечивают неблокирующую обработку, высокую пропускную способность и низкую задержку. Разделение данных на постоянные (PostgreSQL) и временные (Redis) позволяет эффективно использовать ресурсы и масштабировать систему горизонтально.

Предложенная архитектура полностью соответствует требованиям RFC 6749 и может служить надёжной основой для дальнейшего развития, включая поддержку OpenID Connect, расширенных политик безопасности, эндпоинтов интроспекции и ревокации, а также интеграции с внешними системами.
